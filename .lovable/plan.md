# Настраиваемый адрес отправителя писем

Сейчас все письма уходят от жёстко прописанного `Event Hub <noreply@event-hub.by>` — поменять адрес можно только через код. Добавляем управление отправителем прямо в админке, отдельно по каждому типу писем.

## Что появится

В «Настройки → Письма» новая вкладка **Отправители**. Для каждого типа писем задаются:

- **Имя отправителя** (что клиент видит в списке писем, напр. «Event Hub | Отдел продаж»)
- **E-mail отправителя** — любой адрес, в том числе внешний (напр. `sales@company.by`)
- **Адрес для ответа (Reply-To)** — куда попадёт ответ клиента
- Флаг «использовать общие настройки», чтобы не заполнять каждый тип вручную

Типы писем:

| Тип | Что охватывает |
| --- | --- |
| По умолчанию | базовые значения для всех остальных |
| Заказы | подтверждение, оплата, статусы, отмена |
| Коммерческие предложения | отправка КП и КП Промо клиенту |
| Заявки и лиды | письма клиенту по заявке, уточнения |
| Авторизация | регистрация, восстановление пароля, magic-link |
| Рассылки | кампании |
| Служебные (админам) | внутренние уведомления команды |

Рядом — предпросмотр строки, как её увидит клиент: `Имя <адрес>`, и кнопка «Отправить тестовое письмо» на свой e-mail.

## Важный нюанс про внешние адреса

Физическая отправка всегда идёт с проверенного домена event-hub.by — иначе письма попадут в спам или будут отклонены. Поэтому:

- если указанный адрес на домене event-hub.by — он ставится в поле «От» напрямую;
- если адрес внешний (`@gmail.com`, `@company.by` и т.п.) — в «От» подставляется технический адрес на event-hub.by с вашим именем отправителя, а внешний адрес автоматически прописывается в Reply-To, чтобы ответы приходили именно туда. В интерфейсе это поясняется подсказкой прямо у поля.

Так адрес «откуда пришло письмо» управляется вами, а доставляемость не страдает.

## Технические детали

- Таблица `public.email_senders`: `kind` (PK, текст: `default`, `orders`, `quotes`, `leads`, `auth`, `campaigns`, `admin`), `from_name`, `from_email`, `reply_to`, `inherit_default`, `updated_at`. GRANT только `authenticated` (чтение) и `service_role`; RLS — запись/чтение для admin/manager через `has_role`.
- Общий серверный хелпер `src/lib/email/sender.server.ts`: `resolveSender(kind)` — читает настройки через `supabaseAdmin`, наследует `default`, валидирует адрес, применяет правило «внешний адрес → From на проверенном домене + Reply-To», кэширует результат на процесс.
- Точки подстановки (сейчас в каждой свой хардкод `FROM_ADDRESS`): `src/lib/admin-email.server.ts`, `src/lib/campaigns.functions.ts`, `src/lib/order-notifications.functions.ts`, `src/lib/email-templates.functions.ts`, `src/routes/lovable/email/transactional/send.ts`, `src/routes/lovable/email/auth/webhook.ts`. Константа `SENDER_DOMAIN` (`notify.event-hub.by`) не меняется — это технический домен доставки.
- Server fn `src/lib/email-senders.functions.ts`: `listEmailSenders`, `updateEmailSender`, `sendSenderTest` — все под `requireSupabaseAuth` + проверкой роли admin/manager.
- UI: вкладка в `src/routes/admin.settings.emails.tsx` — форма по типам, валидация e-mail, предпросмотр `Имя <адрес>`, автосохранение по кнопке, тестовое письмо.
- Миграция засеивает строку `default` текущими значениями (`Event Hub`, `noreply@event-hub.by`), поэтому поведение до настройки не меняется.

## Порядок работ

1. Миграция таблицы `email_senders` + сид значений по умолчанию.
2. Хелпер `resolveSender` и подключение во всех точках отправки.
3. Серверные функции чтения/записи/теста.
4. Вкладка «Отправители» в настройках писем.
